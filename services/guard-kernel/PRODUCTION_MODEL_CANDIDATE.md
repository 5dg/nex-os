# Candidate model preparation boundary

The candidate route is unqualified and unavailable. Environment profile parsing
and the stock Guard binary do not select it, and candidate PrepareExecution,
result access, phase checks, authorization, completion, state and approval deny
before returning source data or authorizing an effect. An explicitly injected
embedding is not a production configuration or deployment.

The proposed candidate policy binds a separately trusted policy identity and
digest to an exact tenant, route, AWS account and role, GovCloud region,
foundation model, standard or FIPS endpoint, question content/version and
classification, fixed supported template, token limit and feature set. The
account string and model ARN do not prove which credentials will call AWS.
Before any effect admission, a separate trusted authority must authenticate the
actual receiver workload and instance, the exact credentials, their current STS
account and role, the operation, digest, policy and current fence; the receiver
must use those same credentials for its one provider call. This authority,
customer trust configuration and an effect-spanning fence are not implemented.

The additive candidate context is separate from existing v2/v3 payload and
manifest encodings and binds the existing v3 context/digest to the candidate
policy. No previous row is rewritten or upgraded. The proposed source-document
and original-session bindings are default-disabled and receive no grants in the
migration. Their issuer, lifecycle, revocation and least-privilege role controls
must be provisioned and verified independently. A job owner or a raw browser
cookie is not an authenticated original session.

The draft preparation helper is intentionally unreachable and returns no
prompt. It queues a stable operation-bound audit event in the same transaction
as the candidate context, rather than appending external evidence before
commit. Authenticated dispatch and proof-marking are not connected to this
helper; neither this transaction nor a pending row is an evidence anchor. An
ambiguous commit, lost append response, journal failover or possible rollback
requires independently verified nonrollback custody or paused admission and
authenticated reconciliation. Before opening preparation, verify the complete
dispatch and proof path and recheck current user/session and policy authority
at release. Never infer a safe retry solely from apparent evidence success.

Candidate readiness also requires actual restricted-role database tests,
historical v2/v3 preservation checks, current policy/user/tenant/session
revocation and expiration tests, receiver account-attestation tests, and
independent failover/recovery and live deployment verification. No user-facing
production capability is implied by the candidate policy or schema.
