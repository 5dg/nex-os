# Alpha 0.3 synthetic qualification trust contract

Status: frozen interface version 1, approved by the lead auditor for implementation. This profile verifies protocol behavior with synthetic data and private test PKI. It is not production, FIPS validation, CUI admission or compliance authorization.

## Profiles

`NEX_PROFILE` is `development` (default) or `synthetic-qualification`. `production` and unknown values reject startup. `APP_ENV` remains `development` for both synthetic profiles; no existing production prohibition is removed. `NEX_PROFILE` is authoritative for route availability: qualification disables persona vending, the development laboratory and `/v1/models/invoke` even though `APP_ENV` remains development. The qualification profile requires complete verified trust/identity/provider configuration and forbids live AWS/Bedrock adapters before SDK construction even if credentials or provider variables are present. `MODEL_PROVIDER` must be `development`; `local://synthetic-generator` is a logical identity, never a dialable user URL.

Development preserves the explicit Alpha 0.2 fixture, static capability keys, manifest v2 and plaintext localhost/isolated development networks. Qualification requires manifest/payload version 3 and cannot negotiate down to v2, plaintext or unsigned control events. Existing manifests, approvals, receipts, signatures and migration checksums remain historical facts.

## Shared configuration and Go API

`packages/trust` owns `Profile`, `Development`, `Qualification`, `ParseProfile(string)`, `FromEnv()` and shared service roles. `FromEnv` reads `NEX_PROFILE` only; clients may use explicit profiles in isolated tests. It rejects `production`. `Config` loads the immutable process trust snapshot: `NEX_TLS_CA_FILE`, `NEX_TLS_CERT_FILE`, `NEX_TLS_KEY_FILE`. Qualification requires all three PEM files and an own certificate role matching the requested process role. Private material is never logged.

Certificate identity is exactly one URI SAN `spiffe://nex.local/service/<role>`, where role is `workspace`, `control`, `guard`, `model`, `export`, `evidence`, `worker`, `opa` or `oidc`. Server certificates also contain the service DNS SAN used in the configured URL/address. No wildcard URI, CN fallback, forwarding-header or caller-supplied peer-role interpretation is allowed. Server chain/DNS and exact URI are both checked. Qualification uses TLS 1.3 and the pinned Go standard TLS backend / Rust rustls 0.23 ring backend solely as test cryptography, with no validation claim.

Go shared API: `Load(profile, role) (*Config,error)`; `(*Config).HTTPClient(peer Role, timeout time.Duration) (*http.Client,error)`; `(*Config).ServerTLS(requireClient bool) (*tls.Config,error)`; `(*Config).GRPCClientTLS(peer Role, serverName string) (*tls.Config,error)`; `(*Config).CheckPeer(*tls.ConnectionState, []Role) error`; `(*Config).Middleware([]Role,http.Handler) http.Handler`; `ServeHTTP(ctx,address,handler,*Config,requireClient) error`; `(*Config).PerRPCCredentials(peer Role) credentials.PerRPCCredentials`; `CheckURL(raw string) error` on Config. Exact Role constants: `Workspace`, `Control`, `Guard`, `Model`, `Export`, `Evidence`, `Worker`, `OPA`, `OIDC`. `Config` carries `Profile` and `Role`. Qualification HTTP clients reject non-HTTPS URLs on every RoundTrip and disable all automatic redirects (`http.ErrUseLastResponse`); `CheckURL` also rejects credential-bearing URL userinfo/fragment. `CheckOwn() error` validates current process identity and is exposed for final-effect checks. Qualification clients reject non-HTTPS URLs via `CheckURL`; development preserves explicit HTTP. OIDC/browser TLS is server authentication, not mandatory browser certificates. Existing body-bound capabilities remain an additional scope check on service requests.

Trust snapshots are loaded at process start; rotation means restart/recreate that process with new valid files, not silent hot reload. Per HTTP request and per gRPC RPC, verify current peer/own certificate NotBefore/NotAfter, chain and exact role so an already-established connection cannot outlive identity validity. A replaced root/leaf revokes old identity after the coordinated process restart; no immediate distributed CRL/OCSP claim. TLS handshake timeout 3s, dependency/client timeout at most 10s (model execution 45s), server header timeout 3s, bounded body/decode 128KiB HTTP / 256KiB gRPC. Rust/Go database acquisition/connect <=3s, statement <=3s, lock <=2s, overall request <=15s except bounded model effect. Cancellation/rotation cannot turn an ambiguous effect into safe retry. Recheck current peer/own validity after awaited policy/signing dependencies immediately before granting authority, and immediately before the receiver effect. HTTP qualification clients disable keep-alive for bounded handshake revalidation; gRPC uses per-RPC verified connection credentials in addition to peer-role interception.

## Peer-role and endpoint matrix

| Server/endpoint | Permitted caller |
|---|---|
| Guard Evaluate, PrepareExecution, DecideApproval | control |
| Guard CheckReadiness | control, model, export; no execution grant |
| Guard AuthorizeExecution, ExecutionState, CompleteExecution | model for model operations; export for export operations |
| Model /execute,/status | control |
| Export /execute,/status | control |
| Evidence /append/control,/challenge/control | control |
| Evidence /append/kernel,/challenge/kernel | guard |
| Control /internal/work/claim,/internal/work/*/step | worker plus existing worker scope |
| Control /v1 user routes | workspace plus separate API access JWT and DB membership/delegation |
| Control /v1/status | workspace mTLS only; minimal profile/provider/synthetic status, no user data; explicit pre-login readiness exception |
| OPA read source/decision endpoints | guard only; no management write capability |
| OIDC discovery/JWKS/token/authorization | declared issuer HTTPS policy; browser authorization endpoint uses normal HTTPS |
| Browser workspace | HTTPS server authentication and protected server session |

Service identity grants no user/tenant/approval permission. The kernel continues independently resolving protected authority and exact manifest binding. Liveness is bounded `/healthz` and conveys no execution readiness. On an mTLS listener it still requires a valid client certificate; no whole-listener relaxation. A separate unauthenticated liveness listener, if used, is loopback-only and contains no state/identity details. Credential-bearing endpoints and readiness use declared caller identities. Browser TLS termination may use a co-located edge only when its Next.js hop is exclusively loopback in the same network namespace, Next binds 127.0.0.1, and spoofable forwarding headers confer no trust; cross-service plaintext is forbidden.

## Database and OPA

Qualification PostgreSQL uses `DATABASE_URL`/`DATABASE_URL_FILE` with `sslmode=verify-full`, DNS `postgres`, explicit `NEX_DB_CA_FILE` (separate or same test root) and existing distinct role/password files. Rust NoTls and Go admin/plaintext fallback are prohibited. No need for PostgreSQL client certificates in this slice; verified server TLS plus minimal unique SQL credentials is the contract. New migration 008 is reserved to B. A alone coordinates Go grants against new columns. OPA transport uses its `opa` service certificate; kernel client `guard`; only the immutable expected bundle/source is accepted. If native OPA exposes only CN-based client identity, an E-owned co-located allowlisting TLS edge (`scripts/qualification-policy-edge/**`) may verify exact SPIFFE role and forward only allowed decision/source paths to OPA bound exclusively to loopback in the same network namespace; the OPA management endpoint is never published or reachable from other namespaces. This does not add a policy module or weaken source checking. Kernel internal decisions call a private trusted evaluation function, never synthetic gRPC requests or forged certificate extensions. Extra authorization policy content must not weaken that source check.

## Browser identity

Qualification uses fixture authorization code + PKCE S256, state and nonce, fixed callbacks and server sessions. API JWT format is deliberately one supported fixture profile: JWS `typ=at+jwt`, `alg=RS256`, exact HTTPS issuer, audience `nex-api`, `client_id=nex-workspace`, nonempty subject, required `exp`/`iat`, valid optional `nbf`, scope containing `nex:access`. Access JWT lifetime is at most 900s, `iat`/optional `nbf` admit at most 30s future skew, and `kid` is nonempty. ID tokens are only BFF login assertions with audience `nex-workspace` and nonce; they are never API credentials. Unsupported opaque/provider profiles remain closed/deferred.

Environment: `OIDC_ISSUER`, `OIDC_AUDIENCE=nex-api`, `OIDC_CLIENT_ID=nex-workspace`, `OIDC_REQUIRED_SCOPE=nex:access`, `OIDC_CLIENT_SECRET_FILE`, `WORKSPACE_ORIGIN`, `OIDC_REDIRECT_URI=<WORKSPACE_ORIGIN>/auth/callback`. Local canonical origins are `WORKSPACE_ORIGIN=https://workspace.nex.test:9443` and `OIDC_ISSUER=https://issuer.nex.test:9444`; E gives the same names Docker aliases and matching DNS SANs. F host test clients may resolve them to loopback while preserving SNI/Host and verifying the test CA; no TLS-disable flags. The fixture client is confidential: `OIDC_CLIENT_SECRET_FILE` holds its secret, token endpoint authentication is `client_secret_basic`, and PKCE S256 is additionally mandatory. No secret is passed through browser routes, logs or URLs. `/auth/login`, `/auth/callback`, `/auth/logout`, `/api/session` are C-owned. Tokens remain in bounded server memory sessions; HttpOnly/Secure/SameSite cookies, CSRF/origin validation, callback one-use, session expiry/logout/restart invalidation are required. It is a single-instance synthetic store, not production session persistence. Browser fields cannot select subject/tenant/roles. `GET /v1/me` requires workspace peer plus strict access JWT and returns `{issuer,subject,user_id,tenant_id,delegation_id,permissions}` resolved from current DB membership; delegation is the first currently valid owned delegation or empty for an approver. BFF requires its access subject/issuer to match the verified login assertion before opening a session. No claim-based tenant/permission assignment. Existing issuer+subject DB mapping and current permissions/delegations remain authoritative; unknown subjects deny, no automatic privilege provisioning.

## Canonical model/input contract v3

`Generation` adds explicit `manifest_version=3`, `provider`, `region`, `model_id`, `effective_endpoint`, `features`, `template_version`, `question_catalogue_id`, `question_catalogue_version`, `question_classification`. `Export` adds `manifest_version=3`; v2 omitted/zero fields retain exactly their old encoding in development. Qualification requires 3 and rejects mixed/omitted fields. `GenerationResult` retains provider/model_id and receivers/kernel compare them to the sealed tuple.

The only qualification route is route_id `dev-model`, provider `development`, region `local`, model_id `deterministic-review-v1`, effective_endpoint `local://synthetic-generator`, empty features (nil and empty mean the same; duplicates/unknown values rejected), template `review-template-v2`, max_tokens 256. Features are a sorted unique set encoded as count + individual length-prefixed strings. There is no adapter fallback or live SDK construction.

The only first-slice question is trusted catalogue ID `access-review-controls`, version `v1`, text `What access review and export controls apply?`, classification `internal`. `CreateJob` adds `question_catalogue_id`; qualification rejects nonempty raw `question`, resolves the administrator-owned catalogue text/version/classification and stores immutable binding. Database names frozen for migration 008: `question_catalogue(id,version,question,classification,enabled)`; jobs adds `question_id`, `question_version`, `execution_profile` (legacy default development); route columns `provider`, `region`, `model_id`, `effective_endpoint`, `features`, `template_version`; `document_admissions(tenant_id,resource_id,version,content_digest,profile)` explicitly binds the administrator-admitted synthetic fixture digest. A qualification kernel requires the persisted job profile to match and a matching synthetic document admission; neither an ID prefix nor an arbitrary existing body grants synthetic admission. A only seeds admission digests for the exact predefined fixture body and never relabels edited bodies. Go INSERT grants add only question_id/question_version/execution_profile; catalogue/admissions/routes remain SELECT-only for runtime roles. Document and question must both be admitted; aggregate order is public < internal < confidential < restricted, with unknown/restricted denied. Go cannot modify catalogue, protected job inputs or route metadata. B owns additive schema/seed contract and A adjusts only named Go INSERT/SELECT grants. Source/template/question/route changes need fresh manifests and applicable approvals, never a v2 upgrade.

Digest v3 domain is `nex.execution.payload.v3\0`. Canonical UTF-8 fields use unsigned big-endian u64 byte lengths. Model fields in order: `model`, decimal manifest_version, operation_id, tenant_id, route_id, classification, prompt, decimal max_tokens, provider, region, model_id, effective_endpoint, template_version, question_catalogue_id, question_catalogue_version, question_classification, decimal feature_count, each feature in sorted order. Export fields: `export`, decimal manifest_version, operation_id, tenant_id, destination_id, content, request_digest. A owns vectors/generated contracts; B independently implements the same expected vectors. Qualification model/export `/status` use distinct capability audiences `model.status`/`export.status`; `/execute` retain `model.execute`/`export.execute`. Explicit development keeps baseline audiences. D exposes `broker.Client.StatusClient()` to copy scope/transport safely; A reconciliation uses it.

## Guard and authenticated signing readiness

Additive gRPC: `CheckReadiness(ReadinessRequest{}) -> ReadinessResponse{ready:bool,profile:string}`. Only control/model/export peers may call it. B bounds independent DB/schema, pinned OPA default-deny and signing-challenge checks; it never grants execution. A exposes `guard.Client.Readiness(ctx) error` (development may preserve existing Health), and `NewRPCWithTrust(address string, legacyKey []byte, config *trust.Config)`. Qualification gRPC authority comes exclusively from verified certificate role; legacy bearer metadata is not an alternative or required identity. Development retains the old explicit key constructor.

## Authenticated signing readiness

Evidence challenge request `POST /challenge/{control|kernel}` carries existing producer capability audience `evidence.challenge.<producer>` over `{nonce:<64 lowercase hex>}` and matching mTLS role. Reply fields: `producer`, `nonce`, `key_fingerprint` (`sha256:` + lowercase SHA256 of raw 32-byte public key), `signature` (base64url without padding). Signature bytes are length-prefixed UTF-8 producer, nonce, fingerprint and fixed `spiffe://nex.local/service/evidence` under domain `nex.evidence.readiness.v1\0`. Client supplies 32 random bytes, 3s deadline, checks exact nonce/producer/URI/pinned public key/fingerprint/signature. Server verifies single-writer custody/storage health without appending a journal event. Wrong signing client identity or a valid-looking wrong pinned key cannot report execution-ready. Existing signed event/receipt formats remain unchanged.
